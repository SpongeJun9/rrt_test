# 03 定位与硬件接口检查

## 先确认设备和配置

雷达使用 `src/pb2025_sentry_nav-main/pb2025_nav_bringup/config/reality/mid360_user_config.json`（由原导航 YAML 引用），需核对本机网卡 IP、雷达 IP 与实际接线。串口默认 `/dev/ttyUSB0`、115200，核对 `src/lh_rm2025_core/core_serial/config/core_serial_config.yaml`，并确认当前 Linux 用户可访问设备。

完整启动默认 `nav_profile:=original`：使用 `src/pb2025_sentry_nav-main/pb2025_nav_bringup/config/reality/nav2_params.yaml` 的参数，保留 Point-LIO、GICP、地形感知、Omni PID、前瞻、局部/全局代价地图、速度平滑和 fake_vel 参数。当前原文件配置控制器 ±8 m/s、平滑器每轴 ±2.5 m/s、圆形 robot_radius=0.2 m、inflation_radius=0.4 m、init_spin_speed=3.14。这里记录的是原配置，不能据此推断真实车体尺寸或实测速度。

`site.yaml` 保留 RAG 方法、种子、预算、任务超时和记录参数。默认完整入口从原导航配置读取 RAG 净空半径、规划中心 TF、速度观测上界及 Goal Checker 容差；运行时读回参数并核对是否与原文件一致。RAG 使用原始 `/map`，由自身做碰撞净空检查；原 Nav2 的 inflation_radius 保留在代价地图中，不能把它当作 RAG 额外必加的车体半径。

只有显式 `nav_profile:=validation` 时，才生成此前的 0.3 m/s、600×600 mm 加四周 50 mm、矩形 footprint 和关闭 fake_vel 初始自旋的专用配置。独立 `run_trial.sh` 默认也沿用该验证设置。不要把两个配置的结果混在同一论文试验批次。

## 启动后检查

按第 4 份指南启动整套验证入口，先不点导航目标。另一个终端加载原工作区环境：

```bash
ros2 node list
ros2 topic hz /livox/lidar
ros2 topic hz /odometry
ros2 run tf2_ros tf2_echo map base_footprint
# original 模式实际交给规划器的中心帧，沿用原全局代价地图
ros2 run tf2_ros tf2_echo map gimbal_yaw_fake
```

逐条运行，频率检查用 Ctrl+C 退出。观察稳定数据和连续 TF；topic 有发布者不代表定位正确。重定位应使地图中的机器人、实时墙面和二维障碍重合。

| 项目 | 默认接口 |
|---|---|
| 静态二维地图 | `/map` |
| 全局代价地图/增量 | `/global_costmap/costmap`、`/global_costmap/costmap_updates` |
| 局部代价地图/增量 | `/local_costmap/costmap`、`/local_costmap/costmap_updates` |
| 车体外廓 | `/global_costmap/published_footprint`、`/local_costmap/published_footprint` |
| 全局三维 PCD（蓝色） | `/relocalization/global_map`，Reliable / Transient Local |
| 实时配准点云（黄色） | `/registered_scan` |
| 规划中心定位 | original：`map → gimbal_yaw_fake`；validation：`map → base_footprint` |
| 里程计 | `/odometry` |
| 地形感知 | `/terrain_map`、`/terrain_map_ext` |
| 跟踪 Action | `/follow_path` |
| 控制速度 | `/cmd_vel_controller` |
| 平滑后速度 | `/cmd_vel_nav2_result` |
| 变换后/串口输入 | `/cmd_vel` |

首次重定位建议从建图起点附近、相近朝向开始。若位置明显错位，RViz 的 **2D Pose Estimate** 给出粗略初始位姿，再观察点云与地图是否稳定重合。它发布 `/initialpose`，只用于定位，不触发 RAG 规划。

专用 RViz 基于原工程 `nav2_default_view.rviz`，默认显示原 TerrainMapExt 强度着色点云、RobotModel、全局/局部代价地图、外廓和局部跟踪信息，使用二维俯视视角。附加的 `Global PCD map`（蓝色）与 `Live registered scan`（黄色）默认关闭，定位调试时可以勾选；全局 PCD 由重定位节点载入并在完成原有外参变换后发布一次，后启动的 RViz 也能接收。

专用 RViz 的 `Global Planner` 和 `Controller` 分组叠加 `Global Costmap`、`Local Costmap` 和两个 Polygon 外廓。彩色膨胀来自原 Nav2 的代价地图，原始 `/map` 本身仍为黑白图。地图消息使用 Transient Local，增量更新使用 Volatile；因此 `always_send_full_costmap: false` 时仍能持续显示变化。原 TerrainMapExt 的强度着色与附加的蓝/黄色点云可单独开关，以免遮挡膨胀色层。

持续出现 `GICP did not converge` 时，尚不能认定定位正确。保持静止，用 **2D Pose Estimate** 在地图上标出机器人真实位置并拖出真实朝向，继续核对墙面点云重合及 TF 连续性，再给导航目标。默认初始位姿接近原点，重启位置改变后不一定能直接收敛。

## 原源码的关节反馈差异

模型的 joint_state_publisher 订阅 `serial/gimbal_joint_state`，当前 `core_serial` 源码未发布该关节反馈，只广播 `odom_v → gimbal_link`。模型默认零关节值不能替代真实云台反馈。若实车有额外反馈节点，应保持运行并关闭重复模型发布；没有正确反馈时，固定云台/底盘相对姿态并核对实际外参，不能假设活动关节 TF 正确。

需要核对的关键链是 `base_footprint → gimbal_yaw → front_mid360`，以及原 loam/sensor 接口建立的 `odom → base_footprint`。出现 TF 报错时先解决该链，再执行论文任务。

当前串口导航发送包仅携带 x/y 平移，不发送导航 yaw 指令。original 保留原 enable_rotation=false、yaw_goal_tolerance=6.28 和 fake_vel 自旋字段；停止确认仍检查实际里程计角速度与 TF 稳定性，不把未发送到电控的 angular.z 字段当作实测旋转。当前试验主要验证平面路径执行，不能据此宣称验证了终点朝向控制。

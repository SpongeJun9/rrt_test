# 03 定位与硬件接口检查

## 先确认设备和配置

雷达使用 `src/pb2025_sentry_nav-main/pb2025_nav_bringup/config/reality/mid360_user_config.json`（由原导航 YAML 引用），需核对本机网卡 IP、雷达 IP 与实际接线。串口默认 `/dev/ttyUSB0`、115200，核对 `src/lh_rm2025_core/core_serial/config/core_serial_config.yaml`，并确认当前 Linux 用户可访问设备。

试验配置：`rag_rrt_sentry_validation_v1/rag_rrt_sentry_validation_v1/src/rag_rrt_real_validation/config/site.yaml`。默认 600×600 mm 加四周 50 mm 余量只是预设，实测实际外廓、突出部件与中心 TF 后修改。默认最大平移速度 0.3 m/s。

完整验证入口会自动生成低速控制、矩形 footprint、关闭控制器旋转和 fake_vel 初始自旋的专用配置，不改写原导航 YAML。下位机自身的自旋模式仍需由原电控模式关闭。

## 启动后检查

按第 4 份指南启动整套验证入口，先不点导航目标。另一个终端加载原工作区环境：

```bash
ros2 node list
ros2 topic hz /livox/lidar
ros2 topic hz /odometry
ros2 run tf2_ros tf2_echo map base_footprint
```

逐条运行，频率检查用 Ctrl+C 退出。观察稳定数据和连续 TF；topic 有发布者不代表定位正确。重定位应使地图中的机器人、实时墙面和二维障碍重合。

| 项目 | 默认接口 |
|---|---|
| 静态二维地图 | `/map` |
| 机器人定位 | `map → base_footprint` |
| 里程计 | `/odometry` |
| 地形感知 | `/terrain_map`、`/terrain_map_ext` |
| 跟踪 Action | `/follow_path` |
| 控制速度 | `/cmd_vel_controller` |
| 平滑后速度 | `/cmd_vel_nav2_result` |
| 变换后/串口输入 | `/cmd_vel` |

首次重定位建议从建图起点附近、相近朝向开始。若位置明显错位，RViz 的 **2D Pose Estimate** 给出粗略初始位姿，再观察点云与地图是否稳定重合。它发布 `/initialpose`，只用于定位，不触发 RAG 规划。

## 原源码的关节反馈差异

模型的 joint_state_publisher 订阅 `serial/gimbal_joint_state`，当前 `core_serial` 源码未发布该关节反馈，只广播 `odom_v → gimbal_link`。模型默认零关节值不能替代真实云台反馈。若实车有额外反馈节点，应保持运行并关闭重复模型发布；没有正确反馈时，固定云台/底盘相对姿态并核对实际外参，不能假设活动关节 TF 正确。

需要核对的关键链是 `base_footprint → gimbal_yaw → front_mid360`，以及原 loam/sensor 接口建立的 `odom → base_footprint`。出现 TF 报错时先解决该链，再执行论文任务。

当前串口导航发送包仅携带 x/y 平移，不发送导航 yaw 指令。试验默认关闭旋转且放宽 yaw 容差，主要验证平面路径执行，不能据此宣称验证了终点朝向控制。
